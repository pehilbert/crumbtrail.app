# Frontend design

How the Crumbtrail frontend is built, and why. These decisions were made before implementation started (2026-11-15). When one changes, update this file in the same change.

## Goals

- **Web first, then iOS and Android from the same codebase.**
- **The "Butter & Crumb" design system**, implemented faithfully (see [README.md](README.md#design)).
- **Phase 0 (MVP) screens:** log in, register, profile, edit profile, recipe library, recipe view, new recipe, and new journal entry, on mobile and desktop web.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Angular 22: standalone components, signals, zoneless | The current default; no NgModules |
| Styling | Plain CSS with custom properties from the design system's tokens | Native nesting, `clamp()`, container queries and Angular's component style scoping cover what SCSS would add; one source of truth for tokens |
| Components | Our own `ct-` components | The design system is a custom flat look; a UI kit (Ionic components, Material) would mean overriding its styles everywhere |
| State | Signals in small services | Recipes, journals and profile don't need a store library |
| HTTP | `HttpClient` with interceptors | Auth and error handling in one place |
| Unit tests | Vitest (the CLI's `ng test`) | Generated by the CLI |
| End-to-end tests | Playwright (not set up yet) | |
| Rendering | Client-side only | See below |
| Mobile | Capacitor (added later) | Wraps the same build as a native app |

### Rejected options and why

- **Tailwind:** a second source of truth for tokens, and its utility classes replace the design system's `ct-` component vocabulary.
- **SCSS:** its main remaining benefit is reusable breakpoints. With essentially two layouts, one or two hard-coded breakpoints plus container queries is enough. A file can become `.scss` later if that changes.
- **NgRx or another store:** not needed at this size.
- **Ionic UI components:** see Mobile below. Ionic may still be added later for navigation behavior only.
- **React Native or Flutter:** both are weaker on web, and Flutter's web output is a canvas, which is bad for accessibility and SEO.

## Rendering: client-side only for now

There's no server-side rendering or prerendering.

- **SSR is not a security measure.** All authorization is enforced by the API on every request. SSR adds a Node server to secure.
- **Phase 0 is almost all behind a login**, and with this auth design, a server couldn't render logged-in pages anyway: the refresh cookie is only sent to `/api/v1/auth`, and the access token lives in browser memory.
- **Capacitor needs a client-rendered build.**

**Revisit in Phase 1** for "Share recipes with simple links", so shared recipes get link previews and SEO. Add it with `ng add @angular/ssr` and choose rendering per route: server-render public routes such as `/r/:id`, prerender a landing page, and leave the rest client-rendered.

**To keep that easy, code must not touch browser-only globals** (`window`, `document`, `localStorage`, `navigator`) outside a service that wraps them.

## Auth

The API's contract is in [api/endpoints/auth.txt](api/endpoints/auth.txt). The frontend design:

- **Access token:** a 15-minute JWT, **kept in memory only** (a signal in a service). It is never written to `localStorage`, `sessionStorage` or cookies.
- **Refresh token on web:** the API sets an httpOnly `crumbtrail_refresh` cookie, which JavaScript never sees. Auth calls (login, register, refresh, logout) use `withCredentials: true`.
- **Starting the app:** call `POST /auth/refresh` once. A 200 means the user is signed in; a 401 means they're signed out. Route guards wait for this check to finish.
- **On a 401 from any other call:** an interceptor runs **one** refresh at a time (single-flight; concurrent 401s wait for the same refresh), then retries the original request once. If the refresh returns 401, clear the auth state and go to the login screen.
- **Logout:** call `POST /auth/logout`, then clear the in-memory token.
- **Structure:** an `AuthService` (`core/auth/`) owns the session state, and a `TokenStore` interface hides how the refresh token is kept, with a web implementation that relies on the cookie. A native implementation comes with mobile (below). Everything outside these two only asks `AuthService` for the current user or token, so a later switch to a hosted identity provider stays contained.
- **How it's wired:**
  - `provideAppInitializer` runs `AuthService.start()` (the startup refresh). Guards also await `AuthService.ready`.
  - `authInterceptor` adds `Authorization: Bearer` to `/api/v1` calls. Auth calls are marked with the `AUTH_CALL` context token, so they skip the interceptor: a 401 from login must not trigger a refresh.
  - After login, registration or a refresh for a new user, `AuthService` loads `GET /users/me` itself, with the new token and outside the interceptor, so a 401 there can't wait on the refresh it's part of.
  - If a request got a 401 but the token has already changed since it was sent (another request refreshed first), it retries with the new token without refreshing again.
  - `signedInGuard` protects the app shell and sends signed-out users to `/login?returnUrl=…`; only same-app paths are followed. `signedOutGuard` keeps signed-in users off login and register.
- **Logout and deactivation:** logout calls the API (best effort) and always clears local state. Deactivation (`DELETE /users/{id}`) ends every session on the API, so the app only clears its local state afterwards.

### Avoiding XSS

The httpOnly cookie protects the refresh token, but XSS could still act as the user while the page is open. Recipes and journal notes are text users write, so:

- Never use `bypassSecurityTrust*`, and never bind user text to `[innerHTML]`. Angular escapes interpolated text by default.
- If Markdown is ever added, run it through a sanitizer.
- Deploy with a strict Content-Security-Policy (no inline scripts, `connect-src` limited to the API).
- Keep dependencies few, pinned and audited.

### Hosted identity provider: deferred

The split between web and native is standard practice and isn't a reason to switch. **Revisit at the start of Phase 1:** email verification, password reset and especially social login (which on iOS also requires "Sign in with Apple") are where a provider such as Auth0, Clerk, Supabase Auth or Firebase Auth starts paying off.

## Mobile (later)

- **Capacitor** wraps the built web app. No changes to the web build are needed.
- **Ionic components aren't used**, because they would fight the design system. If native-feeling navigation is wanted (swipe-back, page transitions, bottom sheets, pull-to-refresh), add `@ionic/angular` for just those parts.
- **Tokens on native can't use the cookie.** The app's origin (`capacitor://localhost` on iOS, `https://localhost` on Android) isn't on the API's site, so a `SameSite=Strict` cookie won't be sent.
  - The planned API change: native clients send `X-Crumbtrail-Client: native` when logging in or registering, and get the refresh token in the response body. Each session's delivery method (cookie or body) is fixed at login, so a web session can never trade its cookie for a readable token.
  - The native `TokenStore` keeps the refresh token in the Keychain or Keystore through a secure storage plugin such as `@aparajita/capacitor-secure-storage`. **Never `@capacitor/preferences`**, which stores plain text.
  - It refreshes when the app comes back to the foreground, and clears a leftover Keychain token on the first launch after a reinstall.
  - **Status:** filed as crumbtrail.api issue #4, "Support refresh tokens for native mobile clients" (deferred to the mobile port). The original draft is in [proposals/api-native-refresh.md](proposals/api-native-refresh.md).
- **Design for mobile now:** nothing should depend on hover, tap targets are at least 44px, and the floating tab bar pads by `env(safe-area-inset-bottom)`.

## Styles

```
src/styles/
  tokens.css      generated from the design system's tokens.json
  base.css        reset, body on cream-100, fonts, focus ring
  components.css  shared ct- classes from the design system's bundle.css
src/styles.css    imports the three above
```

- **Use tokens, never hex values:** `var(--butter)`, `var(--space-4)`, `var(--radius-lg)`.
- Component-specific styles go in each component's own `.css` file.
- **Fonts:** Fraunces (display) and Nunito (body) from Google Fonts, loaded once in `index.html`.
- **Two layouts:** mobile (designed at 390px, with a floating tab bar) and desktop (a top bar and a 1280px max-width container). The breakpoint is `768px`; the switch is plain CSS in `shell/shell.css`. Login and register have no desktop mockups, so they keep the mobile column (max 480px) centered on the page.

## Local development

- **Proxy `/api` to the API** (`http://localhost:3000`) with the Angular dev server's proxy config. The app and API then share one origin, which avoids CORS and cookie problems.
- The proxy is `web/proxy.conf.json`. It forwards the browser's `Origin` (`http://localhost:4200`), which the API's CSRF check requires to be in `CORS_ORIGINS`; the API's default already includes it. Browsers accept `Secure` cookies on `http://localhost`, so the API's defaults (`REFRESH_COOKIE_SECURE=true`, `SameSite=strict`) work as they are.
- **In production, the app and API must share a site** (for example `crumbtrail.app` and `api.crumbtrail.app`), or the `SameSite=Strict` refresh cookie won't be sent. Hosting the API on an unrelated domain would break refresh.
